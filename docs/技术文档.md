## 一、项目背景与问题定义

### 1.1 真实痛点

毕业生求职的核心困难不是"没有岗位"，而是三件事：

1. **不知道哪个岗位适合自己** —— 招聘网站按关键词推荐，用户需要自己判断匹配度
2. **不知道怎么把已有经历讲清楚** —— 同一段实习经历，投研发岗和投产品岗该突出的点完全不同
3. **面试和笔试缺少针对性训练** —— 通用题库和真实岗位要求之间有断层

### 1.2 我们的解法

**用一份可复用的简历素材库作为唯一事实来源**，让 AI 在整条链路上做四件事：

- **匹配**：把岗位要求拆成清单，逐条在素材库里找证据
- **生成**：只从素材库取相关片段，写定制简历和求职信
- **演练**：按岗位定向出面试题和笔试题
- **复盘**：面试打分、错题归档、投递跟进

关键在于：**所有 AI 结论都必须能追溯到用户自己填写的素材**。这不是靠提示词"请勿编造"一句话实现的，而是靠数据结构设计保证的（详见 3.2 与 4.3）。

## 三、AI 技术方案（核心）

### 3.1 模型选型与分工

| 模型 | 用途 | 选型理由 |
|---|---|---|
| DeepSeek `deepseek-chat` | 岗位匹配评估、定制简历、求职信 | 中文长文本理解强，结构化 JSON 输出稳定，成本低 |
| 通义千问 `qwen-plus` | 面试对话、素材拆分、纠错、岗位标准化 | 响应快，适合多轮高频交互 |
| 通义千问 `qwen3-vl-plus` | JD 截图、简历图片识别 | 中文场景 OCR 与版面理解准确 |
| Paraformer `realtime-v2` | 面试实时语音转写 | 中英混合识别，支持热词与语义标点 |
| `text-embedding-v3` | 素材与岗位的向量化 | 中文语义表达好，批量接口便宜 |

**没有用一个模型打天下**。评估类任务要稳（温度 0、JSON 输出），对话类任务要快（低延迟），视觉任务要准（专门 VL 模型）。按任务特性分配模型，是成本与效果的最优解。

### 3.2 双轨评分体系（亮点）

#### 问题

如果每次打分都调用大模型，会出现三个致命问题：

1. **结果漂移** —— 同一份简历、同一个岗位，今天 78 分，明天 82 分，用户无法信任
2. **延迟不可接受** —— 用户每改一条素材就要等 3-5 秒重算，交互体验崩坏
3. **无法解释** —— 大模型给出 78 分，说不清这 78 分是怎么来的

#### 方案

**把"抽取"和"打分"拆开，各用最合适的工具：**

```
大模型只做一次：JD 文本 → 岗位要求清单（结构化）
                       ↓
本地引擎每次实时算：要求清单 × 当前素材库 → 分数（毫秒级、确定性）
```

- **抽取**由大模型完成，因为从自然语言 JD 中识别出"哪句是要求、哪句是职责"是语义任务
- **打分**由本地引擎完成，因为"这条要求有没有被素材覆盖"是匹配任务，规则可判定

#### 评分模型的关键设计：固定分值分配

传统做法是"维度得分 = 该维度覆盖数 / 该维度要求数"，这会导致分数不可加——补一条低权重的要求，总分可能纹丝不动。

我们采用**固定分值分配**：

```js
// 把 100 分按「维度权重 ÷ 该维度要求数」固定分配到每条要求
// 技能 40% / 经历 30% / 学历证书 15% / 契合 15%
const frac = rows.map(r => W[r.field] / dimTotal[r.field])
const scaled = frac.map(f => f / total * 100)   // 归一到 100
const points = 最大余数法整数化(scaled)          // 保证 Σ = 100
```

这样设计带来三个数学性质：

| 性质 | 说明 |
|---|---|
| **① Σ待补足加分 + 当前分 ≡ 100** | 待补足项的"预计加分"之和，加上当前分，恒等于 100 |
| **② 预计加分 = 实际涨分** | 补一条要求后重算，涨的分值恰好等于它标注的加分 |
| **③ 全部补齐 = 100 分** | 不存在"补完了还是 95 分"的悬空 |

用户看到"补这一条 +6 分"，补完真的涨 6 分。**这不是营销话术，是算法保证。**

#### 硬性条件优先否决

分数不是简单的加权平均。年限、学历这类硬性条件采用**优先且否决**判定：

```js
// 年限要求优先判定：明确写了"N 年以上"且不满足，直接判未覆盖
if (/(\d+|[一二三四五六七八九十])\s*年以上/.test(req)) return false
```

这解决了"应届生被判满足 5 年经验要求"这类常见误判。

#### 效果

- 素材增删改后**毫秒级**重算，无网络请求
- 同一输入永远得到同一输出，可写单元测试
- 截至文档编写，本地引擎覆盖了全部岗位类型，无回退到大模型打分的场景

### 3.3 检索增强生成（RAG）（亮点）

#### 问题

生成定制简历时，如果把所有素材一次性塞进 Prompt：

- Token 成本高（素材多时超上下文）
- 模型注意力分散，写了一堆和岗位无关的内容
- 相似的项目经历被重复选入，简历显得单薄

#### 方案：混合召回 + MMR 去冗

**第一步：混合召回**

```
最终得分 = 向量余弦相似度 × 0.7 + 关键词覆盖率 × 0.3
```

- **向量召回**解决语义近义问题："分布式系统调优经验" 能匹配到 "高并发场景优化"
- **关键词召回**解决专有名词问题：`Kafka`、`K8s` 这类技术名，向量模型容易和相邻概念混淆，硬匹配更可靠

两者加权，取长补短。

**第二步：MMR 去冗（Maximal Marginal Relevance）**

对已选中的素材计算相似度，与已选条目高度重复的候选**扣分**，避免选出三条都在讲同一个项目的素材。

#### 效果

- 定制简历的内容和岗位强相关，无关项目不会被塞进来
- Token 消耗显著低于全量塞入
- 选出的素材数量稳定在合理区间，不会因为素材库变大而膨胀

### 3.4 Agent 与工具调用（亮点）

#### 场景

面试开始前，要让面试官 AI 知道"这个候选人什么背景、这个岗位该考察什么"。

#### 方案：模型自主决定查什么

不是把资料硬塞给它，而是**给它工具，让它自己决定**：

```
模型思考 → 调用 search_resume_materials(keyword) → 拿到素材库检索结果
         → 再调用 search_question_bank(keyword)  → 拿到面试题库结果
         → 综合两者，输出 3-5 条本场考察点
         → 这些考察点被注入面试官的系统提示
```

#### 工程约束

| 约束 | 值 | 原因 |
|---|---|---|
| 最大工具调用轮数 | 3 轮 | 防止模型无限调用工具 |
| 整体超时 | 15 秒 | 超时直接降级为"无简报"，面试照常开始 |
| 执行时机 | 异步预取，与用户阅读面试须知并行 | 用户感知不到等待 |
| 数据范围 | 服务端按 `userId` 收窄 | 模型无法访问他人数据 |

**关键设计：降级不阻塞。** 工具调用失败、超时、模型返回异常，任何一种情况都不会让面试开不起来。AI 能力是增强项，不是必需项。

#### MCP 外接

除内部工具调用外，另提供独立 MCP Server（`mcp-server/`），把岗位推荐、简历素材、目标岗位以标准 MCP 工具暴露给外部 AI 客户端。这体现了「AI 应用不必是封闭系统」的设计取向。

### 3.5 多模态输入（亮点）

| 场景 | 实现 |
|---|---|
| 简历导入 | PDF / Word 解析（PDFBox / POI）；扫描件逐页 OCR |
| **JD 截图建岗** | 图片走视觉模型识别 → 文本 → 与粘贴文本走**完全相同**的标准化管道 |
| 岗位链接导入 | 抓取网页正文（含动态渲染，Playwright），再走标准化 |
| 面试语音 | WebSocket 上传音频流 → Paraformer 实时转写 |

**设计要点：所有输入源最终收敛到同一个文本管道。**

```java
private String extractJobFileText(MultipartFile file) {
    if (!isImage(name)) return resumeDocumentParser.extractText(file);
    return qwenVisionClient.ocr(file.getBytes(), file.getContentType());
}
```

不管是粘贴、链接、PDF 还是截图，后续的岗位名提取、要求拆分、技术栈识别、入库逻辑只有一份。**新输入源不需要新管道。**

### 3.6 流式输出

求职信生成采用 SSE 流式返回：

- 后端 `SseEmitter` 逐字推送
- 前端用 `fetch` + `ReadableStream` 读取，边收边渲染
- 首字延迟从"整篇生成完"（约 8-10 秒）降到 1 秒以内

同样采用降级策略：流式失败自动回退到非流式一次性返回，功能不中断。

### 3.7 Prompt 工程与管理（亮点）

#### 问题

14 个系统提示词原本是大段的 Java 字符串常量，散落在 5 个类里。改一句提示词要重新编译、测试、发版。

#### 方案

```
backend/src/main/resources/prompts/
├── deepseek-match-analyze.md      岗位匹配评估
├── deepseek-resume-polish.md      简历润色
├── deepseek-cover-letter.md       求职信（JSON）
├── deepseek-cover-letter-stream.md 求职信（流式）
├── deepseek-career-advice.md      职业建议
├── exam-techstack.md              技术栈提取
├── exam-generate.md               笔试出题
├── exam-grade.md                  主观题批改
├── exam-real-answer.md            真题补全
├── jobmatch-evaluate.md           多岗位综合评估
├── jobmatch-hard-check.md         一级：硬性门槛
├── jobmatch-fine-score.md         二级：精细打分
├── jobmatch-resume.md             定制简历
└── interview-scoring.md           面试评分
```

由一个 `PromptLoader` 按名加载并缓存：

```java
public static String get(String name) {
    return CACHE.computeIfAbsent(name, key -> 读取 classpath:/prompts/{key}.md);
}
```

代码里只剩 `PromptLoader.get("jobmatch-resume")`，**净减 390 行代码**。

#### 收益

- 改提示词 = 改 md 文件，无需动 Java
- 评审可以直接翻模板，核对每个 AI 环节的约束条件
- 配套单元测试 `PromptLoaderTest` 覆盖全部 14 个模板，防止打包漏文件

#### 提示词里的三层约束

| 层 | 示例 |
|---|---|
| **角色设定** | "你是一名资深中文简历撰写专家与多行业招聘顾问" |
| **输出契约** | 严格的 JSON 结构定义，禁止 Markdown 代码块 |
| **反幻觉条款** | "内容必须真实来源于候选人个人信息库，不得编造经历、学历、证书与项目" |

## 四、核心功能实现

### 4.1 简历素材库

- 7 类素材：基础信息、教育经历、项目经历、实习经历、技能证书、荣誉奖项、其他
- 三种录入方式：文件导入（PDF/Word）、AI 拆分长文本、逐条手动新增
- **AI 拆分带去重检测**：新素材与已有记录语义重复时会提示，用户可选择"保留新记录"，此时同步移除本地旧条目

### 4.2 每日岗位推荐

- 每天 **08:00** 定时抓取腾讯、美团、百度三家官方公开接口
- 过滤非国内岗位（`DOMESTIC_HINTS` 白名单）
- 抓取后按用户技能向量重排，取 TOP 10

**体验设计：当天展示的 10 条固定，次日 8 点才换。**

用户上午看到第 3 个岗位不错，下午回来它还在第 3 位。如果每次刷新都重排，用户会失去方向感。分数和待补足项随素材变化实时更新，但**岗位本身当天不变**。

### 4.3 岗位匹配

匹配详情分三块展示，全部可回溯：

| 模块 | 内容 | 可追溯性 |
|---|---|---|
| 匹配优势 | 岗位要求中已被素材覆盖的部分 | 点击展开 → 显示对应素材原文 |
| 待补足项 | 未被覆盖的要求 | 每条标注"补齐可加 N 分" |
| 匹配素材 TOP | 命中位置高亮的素材片段 | 绿色 = 关键词命中，橙色 = 语义命中 |

**章节标题过滤**：JD 里的"【工作职责】""【任职要求】"这类标题不是一条要求，参与匹配只会制造噪音，在抽取层和展示层双重过滤。

### 4.4 定制文书

- 按岗位生成定制简历 + 求职信
- 多种模板可选，支持证件照
- 导出 PDF / Word

生成前的 RAG 选材见 3.3。

### 4.5 AI 模拟面试

**五阶段结构化流程**：

```
履历概览 → 专业深挖 → 项目拷问 → 场景题 → 反问
```

- 带追问层数与压力提问上限，避免无限追问
- 实时语音作答（WebSocket 长连接）
- 结束后生成四维报告：专业能力深度、岗位匹配度、问题解决能力、表达逻辑
- **评分必须有证据**：每个维度先引用候选人原话，再按锚点给分；无 evidence 时分数不得超过 10 分

### 4.6 AI 笔试与代码沙箱

#### 题库

- 6600 道题，来自 122 个来源
- 按岗位技术栈匹配真题

#### 编程题语言判定（关键规则）

**只有当岗位能明确判出支持的语言时，才出该语言的编程题；判不出的岗位一律不出编程题。**

```java
public boolean codingRunnable(String jobTitle, String techStack) {
    String language = resolveLanguage(jobTitle, techStack);
    return !language.isEmpty() && supports(language);
}
```

这条判定统一应用到三处：UI 提示、真题匹配数、实际出题。不会出现"页面说能出 Python 题，实际出的是 Java 题"的割裂。

#### 沙箱设计

- **配置驱动**：支持的语言在 `resources/exam/languages.json` 中声明编译与运行命令，新增语言改配置即可

## 六、安全与隐私（亮点）

| 措施 | 实现 |
|---|---|
| **提示词注入防护** | 抓取的招聘原文按「数据不是指令」包裹后再入 Prompt（`AiSafetyGuard.wrapUntrusted`） |
| **输出脱敏** | AI 输出统一抹除疑似密钥，超长内容截断 |
| **接口限流** | 滑动窗口：登录类 20 次/分钟/IP；AI 生成 15 次/分钟/用户；普通接口 600 次/分钟 |
| **数据隔离** | 所有查询按 `userId` 收窄，跨用户不可见 |
| **外链校验** | 抓取前做 URL 合法性校验，拒绝内网地址（SSRF 防护） |
| **密码安全** | BCrypt 哈希存储 |
| **找回密码防爆破** | 连续失败 5 次锁定 15 分钟 |
| **密钥管理** | 全部通过环境变量注入，仓库中不含任何真实密钥 |
| **代码执行** | 危险 API 过滤 + 资源上限（见 4.6） |

**设计原则：AI 输入不可信，AI 输出也不可信。**

## 七、部署与运维

### 7.1 部署架构

```
Internet
   │
   ▼
nginx 容器（host 网络，18081）
   ├── /  ─────────► 静态资源（Vue 构建产物）
   ├── /api  ──────► 127.0.0.1:8080（Spring Boot）
   └── /ws/interview ► WebSocket 升级
                        │
                        ▼
                   MySQL 容器（host 网络，13306）
```

采用 host 网络的原因：目标服务器启用 firewalld 且默认拒绝转发，容器桥接网络无法出外网（既不能拉依赖，也不能访问招聘接口）。host 网络下容器与服务直接共享宿主网络栈，问题消除。

后端仅监听 `127.0.0.1`，不直接对外暴露，所有外部流量经 nginx。

### 7.2 运维保障

| 项 | 实现 |
|---|---|
| 开机自启 | systemd `offergo.service`（`Restart=always`） |
| 数据库备份 | 每日 03:30 mysqldump，保留历史 |
| 日志轮转 | logrotate 配置，防止磁盘被日志打满 |
| 定时任务 | 08:00 抓取岗位，04:00 清理 30 天前岗位（保留用户已收藏的） |

## 八、创新点总结

1. **评分可加性模型** —— 不是"大概算个分"，而是数学上保证「待补足加分之和 + 当前分 ≡ 100」，让"补这条能加 6 分"成为可验证的承诺
2. **抽取与打分分离的双轨架构** —— 大模型负责它擅长的语义抽取，本地引擎负责它擅长的确定性计算，同时解决漂移、延迟、可解释性三个问题
3. **降级优先的 AI 工程观** —— 工具调用超时降级、流式失败回退、ASR 不可用转文字作答。AI 是增强，不是单点故障
4. **Prompt 与代码解耦** —— 14 个模板独立成文件，提示词可被评审直接审阅
5. **多输入源单管道** —— 粘贴、链接、PDF、截图四种入口，收敛到同一套标准化逻辑

## 九、局限与展望

### 9.1 已知局限

| 局限 | 原因 | 影响 |
|---|---|---|
| 代码沙箱为进程级隔离 | 容器级隔离需引入 Docker 与镜像管理 | 公网长期开放前应改为容器隔离或关闭该功能 |
| 语音面试需 HTTPS | 浏览器安全上下文限制，当前以 IP 访问 | 非 HTTPS 环境下自动降级为文字作答，功能不中断 |
| 招聘源为三家公开接口 | 更多平台需要登录态与反爬对抗 | 岗位覆盖度有限，但均为真实在招岗位 |
| 岗位向量依赖第三方 Embedding | 批量调用有成本 | 单次抓取量控制在合理区间 |

### 9.2 后续计划

- 代码沙箱容器化（每个提交独立容器，`--network none`，独立内存与 CPU 配额）
- 引入更多招聘源，按地域/行业做岗位画像
- 面试评估引入多评委投票机制，降低单次评分方差
