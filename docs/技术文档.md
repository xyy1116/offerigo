## 一、项目背景

毕业生求职的核心困难不是"没有岗位"，而是：

1. **不知道哪个岗位适合自己** —— 招聘网站按关键词推荐，用户要自己判断匹配度
2. **不知道怎么把经历讲清楚** —— 同一段实习，投研发岗和投产品岗该突出的点完全不同
3. **面试和笔试缺少针对性训练** —— 通用题库和真实岗位要求之间有断层
4. **简历版本太多、投递量太大，事后完全对不上账** —— 一个认真求职的应届生动辄投出几十上百份简历，为适配不同岗位又会改出好几个版本。投到第三十家时，没人记得：这家投的是哪一版？那个岗位的简历里到底写了项目经历没有？面试电话打过来，翻半天也说不清当时投了什么

第 4 点常被忽略，却是求职后半程最真实的混乱来源。**投递量越大，越需要一本账。**

### 我们的解法

**第一层：用一份可复用的简历素材库作为唯一事实来源。**

AI 在匹配、生成、演练、复盘四个环节工作，所有结论都能追溯到用户自己填写的素材。同一份素材，针对不同岗位生成不同版本的简历——**不是让用户自己改十遍，而是每个岗位自动产出一版适配的**。

**第二层：用一套投递档案把过程记下来。**

每个岗位投了哪一版简历、用的是哪套模板、原件存在哪、进展到哪一步，全部留痕。**多版本简历解决了"投什么"，投递档案解决了"投过什么"。**

两层合起来，求职者从"我记得好像投过"变成"我随时能查"。

# 三、核心能力详解

## 3.1 职业匹配度

> **一句话**：把岗位要求拆成清单，逐条在你的素材库里找证据，用确定性算法算出可解释的分数。

### 3.1.1 四维评分模型

| 维度 | 权重 | 判定依据 |
|---|---|---|
| 技能匹配 | 40% | 技术栈、工具、语言是否具备 |
| 经历匹配 | 30% | 项目、实习、工作经历的对口度 |
| 学历与证书 | 15% | 学历层次、专业、职业资格 |
| 岗位契合 | 15% | 求职意向、自我评价、软素质 |

### 3.1.2 关键设计一：抽取与打分分离

如果每次打分都调用大模型，会出现三个致命问题：**结果漂移**（同一份材料今天 78 分明天 82 分）、**延迟高**（改一条素材等 3-5 秒）、**不可解释**。

所以我们把两件事拆开：

```
大模型只做一次：JD 文本 → 岗位要求清单（结构化）
                       ↓
本地引擎每次实时算：要求清单 × 当前素材库 → 分数（毫秒级、确定性）
```

- **抽取**交给大模型：从自然语言 JD 里识别"哪句是要求、哪句是职责"是语义任务
- **打分**交给本地引擎：判断"这条要求有没有被素材覆盖"是规则任务

### 3.1.3 关键设计二：可加性的固定分值分配

传统做法是"维度得分 = 该维度覆盖数 ÷ 该维度要求数"，这会导致分数不可加——补一条低权重的要求，总分可能纹丝不动。

我们按维度权重**把 100 分固定切分到每一条要求**：

```js
// 技能 40% / 经历 30% / 学历证书 15% / 契合 15%
// 每条要求的分值 = 该维度权重 ÷ 该维度要求条数，再整体归一到 100
const frac   = rows.map(r => W[r.field] / dimTotal[r.field])
const scaled = frac.map(f => f / total * 100)
const points = 最大余数法整数化(scaled)   // 保证 Σ = 100
```

由此得到三条数学性质：

| 性质 | 说明 |
|---|---|
| **① Σ待补足加分 + 当前分 ≡ 100** | 待补足项的预计加分之和，加当前分，恒等于 100 |
| **② 预计加分 = 实际涨分** | 补一条要求后重算，涨的分值恰好等于标注的加分 |
| **③ 全部补齐 = 100 分** | 不存在"补完了还是 95 分"的悬空 |

用户看到「补这一条 +6 分」，补完真的涨 6 分。**这是算法保证，不是营销话术。**

### 3.1.4 关键设计三：硬性条件优先否决

分数不是简单加权平均。年限、学历这类硬性条件采用**优先且否决**判定：

```js
// 明确写了"N 年以上"且不满足，直接判未覆盖
if (/(\d+|[一二三四五六七八九十])\s*年以上/.test(req)) return false
```

这解决了"应届生被判满足 5 年经验要求"这类常见误判。

### 3.1.5 结果可回溯

匹配结果分三块展示，每块都能点回原文：

| 模块 | 内容 | 可追溯性 |
|---|---|---|
| 匹配优势 | 已被素材覆盖的要求 | 点击展开 → 显示对应素材原文 |
| 待补足项 | 未被覆盖的要求 | 每条标注"补齐可加 N 分" + 一键快速补充 |
| 匹配素材 TOP | 命中位置高亮的素材片段 | 绿色 = 关键词硬命中，橙色 = 语义命中 |

**章节标题过滤**：JD 里的「【工作职责】」「【任职要求】」不是一条要求，参与匹配只会制造噪音，在抽取层和展示层双重过滤。

### 3.1.6 快速补充闭环

点击待补足项的「快速补充」，AI 把这条要求改写成第一人称的简历化素材草稿，用户确认后入库，分数立即重算。

这让"匹配度"从静态诊断变成可操作的增长路径。

## 3.2 简历生成与模板

> **一句话**：只从素材库里挑与岗位相关的内容，按岗位类型换一套写法，套模板导出 PDF / Word。

### 3.2.1 RAG 精准选材

生成前先从素材库选材，不是全量塞进 Prompt（token 贵、模型注意力分散、容易写出无关内容）。

**第一步：混合召回**

```
最终得分 = 向量余弦相似度 × 0.7 + 关键词覆盖率 × 0.3
```

- **向量召回**解决语义近义："分布式系统调优经验" 能匹配「高并发场景优化」
- **关键词召回**解决专有名词：`Kafka`、`K8s` 这类技术名，向量模型容易和相邻概念混淆，硬匹配更可靠

**第二步：MMR 去冗**

对候选素材与已选素材计算相似度，高度重复的候选扣分，避免选出三条都在讲同一个项目的素材。

### 3.2.2 六类岗位差异化

同一段经历，不同岗位该突出什么完全不同：

| 岗位类型 | 内容侧重点 |
|---|---|
| 技术研发 | 技术栈、架构设计、性能优化、难点攻克、量化成果（STAR 法则） |
| 产品 | 需求分析、产品规划、用户研究、跨团队协作、业务指标提升 |
| 运营 | 拉新促活、留存转化、活动策划、数据目标与增长成果 |
| 设计 | 设计工具、作品集、设计规范、用户体验与视觉方法论 |
| 市场销售 | 业绩数据、客户资源、渠道开拓、谈判成交、ROI |
| 职能 | 专业资质、流程优化、合规风控、沟通协调、可量化成果 |

Prompt 要求模型先判定岗位类型，再按该类型的结构生成，`jobCategory` 字段回传给前端选择对应模板。

### 3.2.3 四套简历模板

内置四套视觉差异明确的版式，打开弹窗即可预览，无网络等待：

| 模板 | 版式 | 风格 | 适用场景 |
|---|---|---|---|
| **极简单栏** | `single` | 黑白灰低饱和、信息密度高 | 最适配大厂 ATS 系统 |
| **侧边栏双栏** | `sidebar` | 左侧信息栏 + 右侧主体，藏青分区 | 信息层次多，经历丰富 |
| **宽页眉** | `banner` | 顶部通栏深蓝彩带，姓名醒目 | 突出求职意向 |
| **轻商务** | `serif` | 细线分隔 + 墨绿米白，衬线字体 | 稳重克制，职能/管理岗 |

每套模板由「版式 + 主色 + 辅色 + 背景色 + 字体栈」五个参数驱动，导出时统一渲染。

### 3.2.4 导出

| 格式 | 实现 | 注意点 |
|---|---|---|
| PDF | openhtmltopdf | 中文需内嵌字体，模板字号与边距做过分页适配 |
| Word | Apache POI | 生成可二次编辑的 docx |

支持上传证件照，随请求提交，仅用于导出渲染。

### 3.2.5 求职信

简历之外，同步生成一封**针对该岗位**的求职信。

**内容结构**（约 200-350 字）：

| 段落 | 写什么 |
|---|---|
| 开篇 | 应聘岗位与信息来源 |
| 主体 | 2-3 点核心匹配优势，**紧扣该岗位 JD** |
| 结尾 | 加入意愿与感谢 |

约束：只使用与岗位要求直接相关的经历、技能和成果；与岗位无关的项目、课程、兴趣、证书一律不写。

**两条生成链路**：

- **JSON 版**：返回 `subject / greeting / body` 结构，便于展示与二次编辑
- **流式版**：SSE 逐字推送纯文本正文，首字延迟从 8-10 秒降到 1 秒以内

流式失败自动回退到非流式一次性返回，功能不中断。

### 3.2.6 一份素材库，N 个岗位，N 套模板

传统做法是用户自己改简历：投 Java 岗改一版、投大数据岗再改一版，改到第五版时原版已经被覆盖，自己都分不清哪个是哪个。

我们的做法是**素材库只维护一份，版本按岗位现场生成**：

**每一版都根据目标岗位的内容重新组织（六类岗位差异化，见 3.2.2），并且可以套用四套模板中的任意一套导出（3.2.3）。** 同一份素材，投 Java 岗用「极简单栏」，投管理岗用「轻商务」，内容与版式同时适配。

```
        固定不变：简历素材库（教育/项目/实习/技能/证书）
                              │
        ┌─────────┬───────────┼───────────┬─────────┐
        ▼         ▼           ▼           ▼         ▼
     Java 岗    前端岗      算法岗      产品岗    运营岗
     （后端    （前端框架  （算法项目  （需求分析 （活动策划
      +架构）    +工程化）   +论文）     +数据）    +增长）
```

这意味着：

| 传统方式 | OfferiGo |
|---|---|
| 用户手动维护多个文件 | 只有一份素材库，改一处全部生效 |
| 改到后来分不清版本 | 每次生成都是新版本，历史不被覆盖 |
| 不知道某岗位用了哪版 | 投递时记录模板，台账可回查 |
| 换岗位要重写一遍 | 换岗位重新生成，30 秒出结果 |

**版本多不可怕，失控才可怕。** 3.3.5 的「简历模板留痕」正是为这件事兜底——生成得多，也要记得住。

## 3.3 投递记录

> **一句话**：把"投了哪、进展到哪、该跟进谁"管起来，并且留档当次投出的那份简历。

### 3.3.1 投递草稿机制

直接在页面点「投递」就可能产生无效记录（弹窗被拦截、用户中途放弃、岗位页没打开）。

我们的做法：

```
点击「投递」→ 跳转真实岗位页 → 页面确实打开后 → 生成投递草稿
                                                    ↓
                                    回到应用 → 确认 → 转为正式记录
```

草稿不会污染台账，只有用户确认「我确实投了」之后才计入。

### 3.3.2 台账管理

| 字段 | 说明 |
|---|---|
| 投递时间 | 自动记录 |
| 简历 | 当次投出的那份，可上传 / 查看 / 删除 |
| 岗位链接 | 直达原始岗位详情页 |
| 状态 | 自由维护，按状态着色 |
| 备注 | 记录面试反馈、联系人等 |

### 3.3.3 跟进提醒

用户可设置全局跟进间隔（默认若干天）。超过间隔未更新的记录，列表里自动打「该跟进了」标签，首页汇总提示"有 N 条投递已到跟进时间"。

**这把台账从"记账"变成"待办"。**

### 3.3.4 简历归档

每条投递可上传当次实际使用的简历文件（PDF/Word），与库里的素材库分离——素材库是动态积累的，归档是历史快照。

删除投递记录时同步清理归档文件，不留孤儿数据。

### 3.3.5 简历模板留痕

投了这么多家，回看时最容易忘的是：**这一份投的到底是哪版简历？**

确认投递时记录本次使用的简历模板（极简单栏 / 侧边栏双栏 / 宽页眉 / 轻商务），随记录一起入库，在「个人中心 → 我的投递」中以独立列展示。

| 记录内容 | 作用 |
|---|---|
| 投递时间 | 什么时候投的 |
| **简历模板** | 用的哪一套版式，对应什么岗位风格 |
| 简历文件 | 实际投出去的那份原件 |
| 岗位链接 | 回到原始岗位详情 |
| 状态 / 备注 | 进展到哪、有什么反馈 |

四者合起来构成一条完整的投递证据链：**给谁投的、什么时候投的、用什么版本投的、原件在哪。**

### 3.3.6 台账的真实用途

这不是一个"记账本"，而是求职过程的管理台：

- 按状态筛选，一眼看出哪些还在等回复、哪些到期该跟进
- 按关键词搜索，快速找到某家公司的投递
- 到期未更新自动打「该跟进了」标签，首页汇总提示

## 3.4 面试模拟

> **一句话**：按岗位定向提问，实时语音作答，结束后给出带证据的四维评分。

### 3.4.1 五阶段结构化编排

```
履历概览 → 专业深挖 → 项目拷问 → 场景题 → 反问
```

不是让模型自由发挥，而是编排器控制每个阶段问什么、问几层、什么时候收。带追问层数与压力提问上限，避免无限追问把用户逼死。

### 3.4.2 Agent 工具调用生成面试简报

面试开始前，要让面试官 AI 知道"这个人什么背景、这个岗位该考察什么"。

我们的做法不是硬塞资料，而是**给模型工具，让它自己决定查什么**：

```
模型思考 → 调用 search_resume_materials(keyword) → 拿到素材检索结果
         → 再调用 search_question_bank(keyword)  → 拿到面试题库结果
         → 综合两者，输出 3-5 条本场考察点
         → 考察点注入面试官系统提示
```

工程约束：

| 约束 | 值 | 原因 |
|---|---|---|
| 最大工具轮数 | 3 轮 | 防止无限调用 |
| 整体超时 | 15 秒 | 超时降级为无简报，面试照常开始 |
| 执行时机 | 异步预取，与用户阅读须知并行 | 用户感知不到等待 |
| 数据范围 | 服务端按 `userId` 收窄 | 模型无法访问他人数据 |

**降级不阻塞**：工具调用失败、超时、异常，任何一种情况都不会让面试开不起来。

### 3.4.3 视频与实时语音

面试开始前一次性申请摄像头与麦克风权限，进入房间后：

| 能力 | 实现 |
|---|---|
| **视频画面** | 本机摄像头实时预览，模拟真实面试的临场感 |
| **实时语音** | 音频流经 WebSocket 上传 → Paraformer 实时转写 → 大模型生成应答 |

**说明**：视频画面仅用于本地预览（用户自检仪态与表现），不做人脸识别或表情分析，上传到服务端的只有音频轨。这一点在技术上是有意为之——面试评估的依据是**说了什么**，而非**长什么样**。

**三级降级**，任一环节不可用都不阻断流程：

```
摄像头 + 麦克风均可用  → 完整音视频面试
摄像头不可用           → 自动降级为纯语音面试，提示"已降级为纯语音面试"
麦克风也不可用         → 自动降级为文字作答
```

安全上下文限制下（非 HTTPS），浏览器会拒绝授权，前端检测 `isSecureContext` 后直接进入文字作答模式。降级路径见 9.3。

### 3.4.4 证据化评分

报告四个维度，每项 0-25 分，总分由代码聚合：

| 维度 | 考察内容 |
|---|---|
| 专业能力深度 | 是否懂方法、有取舍、能对比替代方案 |
| 岗位匹配度 | 经验与岗位方向的相关性 |
| 问题解决能力 | 拆解问题的系统性与落地能力 |
| 表达逻辑 | 结构性与说服力 |

**评分必须带证据**：

- 每个维度先引用求职者原话，再按锚点给分
- 没有 evidence 时分数不得超过 10 分
- 该维度本轮未充分考察时不得超过 12 分，并注明原因
- **非技术岗不按编程、架构标准打分**，按求职者所在岗位族评价

这避免了"没问到就给中位分"的虚高问题。

### 3.4.5 面试记录留痕

每场面试结束后自动归档，在「个人中心 → 面试记录」中可查：

| 记录内容 | 说明 |
|---|---|
| 面试岗位 | 本场针对哪个岗位 |
| 得分 | 四维加权总分 |
| 时间 | 什么时候练的 |
| 详情 | 完整对话记录 + 逐维度评语 + 证据原话 |

**价值**：面试能力是可以被观察的。练了五场，分数从 62 到 78，哪个维度在进步、哪个一直卡住，翻记录一眼就能看出来。这比"多练几次"这种空话有用。

## 3.5 笔试刷题

> **一句话**：6600 道真实题库，按岗位技术栈定向组卷，编程题用真实语言环境跑。

### 3.5.1 题库

| 项 | 数值 |
|---|---|
| 题目总量 | 6600 道 |
| 来源数量 | 122 个 |
| 题型 | 单选 / 多选 / 简答 / 编程 |

### 3.5.2 两种练习模式

| 模式 | 说明 |
|---|---|
| **专项练习** (`practice`) | 按知识点、题型、难度自由筛题，想做几道做几道 |
| **限时模拟** (`mock`) | 设定时长，模拟真实笔试题量与节奏 |

两种模式共用同一套组卷、批改、错题归档逻辑。

### 3.5.3 岗位定向组卷

从岗位匹配结果一键跳转组卷，带上岗位名称、JD、技术栈，题库按技术栈匹配出题，而不是随机抽题。

### 3.5.4 编程题的语言判定（关键规则）

**只有当岗位能明确判出支持的语言时，才出该语言的编程题；判不出的岗位一律不出编程题。**

```java
public boolean codingRunnable(String jobTitle, String techStack) {
    String language = resolveLanguage(jobTitle, techStack);
    return !language.isEmpty() && supports(language);
}
```

这条判定统一应用到三处：**UI 提示、真题匹配数、实际出题**。不会出现"页面说能出 Python 题、实际出的是 Java 题"的割裂。

### 3.5.5 代码沙箱

| 项 | 说明 |
|---|---|
| 支持语言 | Java / JavaScript / Python / C / C++ |
| 配置方式 | `resources/exam/languages.json` 声明编译与运行命令，新增语言改配置即可 |
| 隔离手段 | 临时目录 + 超时 + 内存上限 + 输出上限 + 并发限制 |
| 安全过滤 | 危险 API 关键字过滤（按语言家族） |

**如实说明**：这是进程级隔离，不是容器级安全沙箱（见第九章）。

### 3.5.6 批改

- **客观题**：按标准答案判定
- **主观题**：AI 批改，核心依据是"答案的核心内容与逻辑是否正确"，**允许同义改写、语序调整**，不因措辞差异判错
- **编程题**：真实编译运行，按测试用例通过情况给分；单题执行失败记 0 分并继续，不让整卷崩掉

### 3.5.7 笔试记录

每份试卷交卷后自动归档，在「个人中心 → 笔试记录」中可查：

| 记录内容 | 说明 |
|---|---|
| 岗位 | 本套卷针对哪个岗位 |
| 类型 | 专项练习 / 限时模拟 |
| 得分 | 卷面得分 / 总分 |
| 时间 | 什么时候做的 |
| 详情 | 逐题回顾：题干、你的答案、标准答案、解析 |

**两种模式共用同一套归档逻辑**，练习和模拟的记录混在一起按时间倒序排列，能直观看到备考轨迹。

### 3.5.8 错题本

答错的题自动进入错题本，按 `paper_id` 与试卷关联：

- **按岗位筛选**：只复习某个岗位相关的错题
- **按题型筛选**：单选 / 多选 / 简答 / 编程
- **错题详情**：原题、你的答案、标准答案、解析、延伸学习建议、错误原因
- **错误次数**：同一知识点反复出错会被记录，暴露真实薄弱环节
- **重做**：可针对错题重新作答，编程题走真实执行环境判分

**错题本不是简单的收藏夹**——它记录了"你为什么会错"，错误原因由 AI 分析后写入，复习时看的是思路偏差而不是答案本身。

## 3.6 每日新职位推送与排序

> **一句话**：每天 8 点自动抓最新岗位，按你的简历重排，当天给你固定 10 条。

### 3.6.1 定时抓取

| 项 | 值 |
|---|---|
| 执行时间 | 每天 08:00（`Asia/Shanghai`） |
| 数据来源 | 腾讯招聘 / 美团招聘 / 百度招聘 官方公开接口 |
| 每次抓取量 | 按用户技能向量定向检索，三源均分 |
| 地域过滤 | 只保留国内岗位（白名单匹配） |

先用当天最新素材刷新技能向量，再用向量去各源检索——**抓的是跟你相关的岗位，不是全量岗位**。

### 3.6.2 排序

抓取结果按用户技能向量相似度重排，取匹配度最高的作为推荐池。

### 3.6.3 体验设计：当天 TOP10 固定

**当天展示的 10 条岗位固定，次日 8 点才换。**

原因很简单：用户上午看到第 3 个岗位不错，下午回来它还在第 3 位。如果每次刷新都重排，用户会失去方向感，也没法跟别人描述"我今天在投的那个"。

实现上按「日期 + 推荐版本」存一份当天的 TOP10，当天内只从中取；跨天后版本变化，自动换新。

**但分数和待补足项仍然实时变化**——素材改了，同样的 10 个岗位分数立刻变。变的只是"哪 10 个"，不是"这 10 个多少分"。

### 3.6.4 数据清理

每天 04:00 清理 30 天前的抓取岗位，**保留用户已加入目标岗位的记录**，避免用户收藏的岗位被定时任务误删。

### 3.6.5 容错

抓取失败（接口变更、网络异常）不影响已有数据，前端继续展示上次结果；抓取到 0 条时写告警日志，不做静默失败。

### 3.6.6 岗位来源可追溯

**每个岗位都标注它从哪来。**

卡片上直接显示来源标签：腾讯招聘 / 美团招聘 / 百度招聘 / BOSS直聘 / 前程无忧 / 猎聘 / 拉勾。

来源不是人工录入的，而是由岗位原始链接的域名自动判定：

```java
private String sourceOf(String sourceUrl) {
    if (域名含 tencent.com)  return "腾讯招聘";
    if (域名含 meituan.com)  return "美团招聘";
    if (域名含 baidu.com)    return "百度招聘";
    ...
}
```

| 用户能看到 | 意义 |
|---|---|
| 来源平台标签 | 一眼知道这岗位来自企业官网还是第三方平台 |
| 原始岗位链接 | 点击可跳回原站核对，确认真实存在 |
| 公司名称 | 与来源交叉验证 |

**为什么重要**：AI 推荐岗位最容易被质疑的就是"这些岗位是真的吗、是不是生成的"。标注来源并允许一键回原站验证，把"你信我"变成"你自己去看"。

这也是我们在产品上的一贯原则：**能让人验证的，就不要让人相信。**

### 3.6.7 一键跳转原站投递

推荐岗位的最终去向是原始招聘页面，不是站内表单：

| 岗位类型 | 跳转逻辑 |
|---|---|
| 推荐岗位 | 直接用抓取到的原始链接打开岗位详情页 |
| 手动添加的岗位 | 后端按公司名与岗位名检索校验后返回链接 |
| 找不到 | 返回空，前端提示，不让用户点进死链 |

打开原站完成投递后回到应用，此时才会生成投递草稿（见 3.3.1）——**平台不代投、不要求授权账号**，用户始终在自己的账号下完成投递。

## 3.7 职业收藏与个人档案

> **一句话**：好岗位留得住，练过的都留下痕迹。

### 3.7.1 收藏即沉淀

每日推荐里看到的岗位，一键「加入我的收藏」即沉淀为**目标岗位**。收藏不是打个标记，而是解锁完整链路：

```
推荐岗位 → 加入收藏（成为目标岗位）
              ↓
        参与匹配评分 · 生成定制简历 · 发起投递 · 定向笔试 · 模拟面试
```

没收藏的推荐岗位只能看，收藏之后才能对它做任何事。这让"收藏"成为整条链路的入口，而不是一个孤立的功能。

### 3.7.2 收藏的稳定性

两个细节：

- **收藏后留在原位**：当天 TOP10 的排序不受影响，按钮变为「已加入我的收藏」并置灰，不会因为收藏动作导致列表重排
- **收藏的岗位不会被清理**：每日 04:00 会清理 30 天前的抓取岗位，但**被收藏的不删**——用户主动标记的东西不能因为定时任务消失

### 3.7.3 个人档案总览

「个人中心」把用户在整个平台上的痕迹汇总成四本账：

| 档案 | 内容 | 价值 |
|---|---|---|
| **我的投递** | 投递时间、岗位、**简历模板**、简历原件、状态、备注 | 投了什么、进展到哪 |
| **面试记录** | 岗位、得分、时间、完整对话与逐维度评语 | 面试能力有没有在进步 |
| **笔试记录** | 岗位、类型、得分、逐题回顾 | 备考轨迹 |
| **笔试错题** | 按岗位/题型筛选，含错误原因与重做 | 薄弱环节在哪 |

四本账互相独立又互相引用：投递记录关联目标岗位，面试记录关联岗位，错题库关联试卷。

**设计意图**：求职是一个持续几周甚至几个月的过程，用户需要的不是一个"用完就走"的工具，而是一个能积累、能回看的档案系统。

# 四、AI 技术底座

> 第三章的七项能力，都建立在这一层之上。

## 4.1 模型选型与分工

| 模型 | 用途 | 选型理由 |
|---|---|---|
| DeepSeek `deepseek-chat` | 岗位匹配评估、定制简历、求职信 | 中文长文本理解强，结构化 JSON 输出稳定，成本低 |
| 通义千问 `qwen-plus` | 面试对话、素材拆分、纠错、岗位标准化 | 响应快，适合多轮高频交互 |
| 通义千问 `qwen3-vl-plus` | JD 截图、简历图片识别 | 中文场景 OCR 与版面理解准确 |
| Paraformer `realtime-v2` | 面试实时语音转写 | 中英混合识别，支持热词与语义标点 |
| `text-embedding-v3` | 素材与岗位的向量化 | 中文语义表达好，批量接口便宜 |

**没有用一个模型打天下**：评估类要稳（温度 0、JSON 输出），对话类要快，视觉类要准。按任务特性分配模型是成本与效果的最优解。

## 4.2 多模态输入

| 场景 | 实现 |
|---|---|
| 简历导入 | PDF / Word 解析；扫描件逐页 OCR |
| **JD 截图建岗** | 图片走视觉模型识别 → 文本 → 与粘贴文本走**完全相同**的标准化管道 |
| 岗位链接导入 | 抓取网页正文（含动态渲染），再走标准化 |
| 面试语音 | WebSocket 上传音频流 → Paraformer 实时转写 |

**关键设计：所有输入源最终收敛到同一个文本管道。**

```java
private String extractJobFileText(MultipartFile file) {
    if (!isImage(name)) return resumeDocumentParser.extractText(file);
    return qwenVisionClient.ocr(file.getBytes(), file.getContentType());
}
```

不管是粘贴、链接、PDF 还是截图，后续的岗位名提取、要求拆分、技术栈识别、入库逻辑只有一份。**新输入源不需要新管道。**

## 4.3 流式输出

求职信与部分生成内容采用 SSE 流式返回：后端 `SseEmitter` 逐字推送，前端 `fetch` + `ReadableStream` 边收边渲染。首字延迟从"整篇生成完"降到 1 秒以内。

## 4.4 Prompt 工程与管理

### 问题

14 个系统提示词原本是散落在 5 个类里的大段 Java 字符串常量，改一句提示词要重新编译、测试、发版。

### 方案

全部剥离为独立模板文件：

```
backend/src/main/resources/prompts/
├── deepseek-match-analyze.md       岗位匹配评估
├── deepseek-resume-polish.md       简历润色
├── deepseek-cover-letter.md        求职信（JSON）
├── deepseek-cover-letter-stream.md 求职信（流式）
├── deepseek-career-advice.md       职业建议
├── exam-techstack.md               技术栈提取
├── exam-generate.md                笔试出题
├── exam-grade.md                   主观题批改
├── exam-real-answer.md             真题补全
├── jobmatch-evaluate.md            多岗位综合评估
├── jobmatch-hard-check.md          一级：硬性门槛
├── jobmatch-fine-score.md          二级：精细打分
├── jobmatch-resume.md              定制简历
└── interview-scoring.md            面试评分
```

由 `PromptLoader` 按名加载并缓存：

```java
public static String get(String name) {
    return CACHE.computeIfAbsent(name, key -> 读取 classpath:/prompts/{key}.md);
}
```

代码里只剩 `PromptLoader.get("jobmatch-resume")`，**净减 390 行代码**。

### 收益

- 改提示词 = 改 md 文件，无需动 Java
- 评审可直接翻模板核查每个 AI 环节的约束
- 配套单元测试覆盖全部 14 个模板，防止打包漏文件

### 提示词的三层约束

| 层 | 示例 |
|---|---|
| 角色设定 | "你是一名资深中文简历撰写专家与多行业招聘顾问" |
| 输出契约 | 严格 JSON 结构定义，禁止 Markdown 代码块 |
| 反幻觉条款 | "内容必须真实来源于求职者个人信息库，不得编造经历、学历、证书与项目" |

## 4.5 MCP 外接

除内部工具调用外，另提供独立 MCP Server（`mcp-server/`），把岗位推荐、简历素材、目标岗位以标准 MCP 工具暴露给外部 AI 客户端。体现「AI 应用不必是封闭系统」的设计取向。

# 六、安全与隐私

| 措施 | 实现 |
|---|---|
| **提示词注入防护** | 抓取的招聘原文按「数据不是指令」包裹后再入 Prompt |
| **输出脱敏** | AI 输出统一抹除疑似密钥，超长内容截断 |
| **接口限流** | 登录类 20 次/分钟/IP；AI 生成 15 次/分钟/用户；普通接口 600 次/分钟 |
| **数据隔离** | 所有查询按 `userId` 收窄，跨用户不可见 |
| **外链校验** | 抓取前校验 URL，拒绝内网地址（SSRF 防护） |
| **密码安全** | BCrypt 哈希存储 |
| **找回密码防爆破** | 连续失败 5 次锁定 15 分钟 |
| **密钥管理** | 全部通过环境变量注入，仓库中不含真实密钥 |
| **代码执行** | 危险 API 过滤 + 资源上限 |

**设计原则：AI 输入不可信，AI 输出也不可信。**

# 七、部署与运维

## 7.1 部署架构

```
Internet
   │
   ▼
nginx 容器（host 网络，18081）
   ├── /  ──────────► 静态资源（Vue 构建产物）
   ├── /api  ───────► 127.0.0.1:8080（Spring Boot）
   └── /ws/interview ► WebSocket 升级
                        │
                        ▼
                   MySQL 容器（host 网络，13306）
```

采用 host 网络的原因：目标服务器启用 firewalld 且默认拒绝转发，容器桥接网络无法出外网（既不能拉依赖，也不能访问招聘接口）。host 网络下容器与服务共享宿主网络栈，问题消除。

后端仅监听 `127.0.0.1`，所有外部流量经 nginx。

## 7.2 运维保障

| 项 | 实现 |
|---|---|
| 开机自启 | systemd `offergo.service`（`Restart=always`） |
| 数据库备份 | 每日 03:30 mysqldump |
| 日志轮转 | logrotate，防止日志打满磁盘 |
| 定时任务 | 08:00 抓取岗位；04:00 清理 30 天前岗位（保留已收藏） |

# 八、创新点总结

1. **评分可加性模型** —— 数学上保证「Σ待补足加分 + 当前分 ≡ 100」，让"补这条能加 6 分"成为可验证的承诺
2. **抽取与打分分离的双轨架构** —— 大模型做语义抽取，本地引擎做确定性计算，同时解决漂移、延迟、可解释性三个问题
3. **推荐结果的"当天锁定"体验设计** —— 岗位固定、分数实时，兼顾方向感与实时性
4. **证据化评分** —— 面试每个维度必须先引用求职者原话才能给分，没证据不给高分
5. **降级优先的 AI 工程观** —— 工具调用超时降级、流式失败回退、语音不可用转文字，AI 是增强不是单点故障
6. **Prompt 与代码解耦** —— 14 个模板独立成文件，提示词可被评审直接审阅

# 九、局限与展望

## 9.1 已知局限

| 局限 | 原因 | 影响 |
|---|---|---|
| 代码沙箱为进程级隔离 | 容器级隔离需引入 Docker 与镜像管理 | 公网长期开放前应改为容器隔离或关闭该功能 |
| 语音面试需 HTTPS | 浏览器安全上下文限制，当前以 IP 访问 | 非 HTTPS 环境下自动降级为文字作答，功能不中断（演示配置见 9.3） |
| 招聘源为三家公开接口 | 更多平台需登录态与反爬对抗 | 岗位覆盖度有限，但均为真实在招岗位 |
| 岗位向量依赖第三方 Embedding | 批量调用有成本 | 单次抓取量控制在合理区间 |

## 9.2 后续计划

- 代码沙箱容器化（独立容器、`--network none`、独立内存与 CPU 配额）
- 引入更多招聘源，按地域/行业做岗位画像
- 面试评估引入多评委投票，降低单次评分方差

## 9.3 演示环境说明：语音面试如何体验

### 背景

语音面试依赖浏览器的 `getUserMedia` API，而该 API **只在安全上下文中可用**——即 `https://` 页面或 `localhost`。当前演示环境以 `http://IP:端口` 形式访问，属于非安全上下文，浏览器会直接拒绝授予麦克风权限。

这不是本项目的问题，是所有依赖麦克风的 Web 应用在 HTTP 下的共同限制。

### 三种访问方式的差异

| 访问方式 | 麦克风 | 面试功能 |
|---|---|---|
| `http://47.104.161.228:18081`（当前演示地址） | ❌ 不可用 | 自动降级为**文字作答**，流程完整 |
| 浏览器白名单配置后访问同一地址 | ✅ 可用 | 可体验完整语音面试 |
| 生产环境：`https://域名` | ✅ 可用 | 可体验完整语音面试 |

**关键设计：降级不阻塞。** 前端启动面试时会检测 `isSecureContext`，不可用时自动切换为文字作答模式，不会报错、不会卡住流程。评委即使不配置任何东西，也能完整走完一场面试，只是用打字代替说话。

### 演示时如何开启语音

若需在评审现场体验语音交互，可在 Chrome / Edge 中把演示地址加入安全来源白名单：

**方式一：浏览器设置**

1. 地址栏输入 `chrome://flags`（Edge 为 `edge://flags`）
2. 搜索 `Insecure origins treated as secure`
3. 状态改为 `Enabled`
4. 在输入框中填入 `http://47.104.161.228:18081`
5. 点击 `Relaunch` 重启浏览器
6. 重新打开演示地址，进入面试页即可授权麦克风

**方式二：启动参数**

```
chrome.exe --unsafely-treat-insecure-origin-as-secure=http://47.104.161.228:18081 --user-data-dir=C:\chrome-demo
```

### 说明

以上白名单配置是演示场景下的备选方式：

- 依赖访问者本机浏览器设置，换设备需重新配置
- 不配置也不影响使用，面试会自动降级为文字作答，其余功能不受影响
- 正式部署时建议通过域名 + TLS 证书满足安全上下文要求，无需任何客户端配置

# 十、产品延伸：B 端（HR 侧）

> **状态说明**：本章描述的是**正在筹备中**的产品方向，尚未上线。当前在线演示的是 C 端（求职者侧）完整功能。此处如实标注，避免与已实现能力混淆。

## 10.1 为什么要做 B 端

> **术语说明**：**C 端**（Consumer）指个人用户，本项目对应求职者；**B 端**（Business）指企业客户，对应 HR 与招聘方。

求职是双向的。C 端解决「求职者找岗位」，B 端解决「HR 找求职者」——**同一件事的两面，引擎天然对称**。

C 端已经验证的核心能力，换个方向就是 B 端需要的：

| 能力 | C 端用法 | B 端用法 |
|---|---|---|
| 匹配引擎 | 求职者看到「这个岗位我多少分」 | HR 看到「这个求职者多少分」 |
| 题库与组卷 | 求职者练习、模拟考试 | HR 发布招聘笔试题 |
| AI 面试 | 求职者自己练手 | HR 用于初筛求职者 |
| 评分报告 | 求职者自我复盘 | HR 拿到结构化评估结论 |

**这不是另起一个产品，而是把同一套引擎调转方向使用。**

## 10.2 规划中的三项能力

### ① 简历匹配排序

```
HR 发布招聘需求（岗位名称、职责、硬性要求、技术栈）
        ↓
批量导入求职者简历（上传 PDF/Word，或对接招聘渠道）
        ↓
匹配引擎逐份解析、逐条比对、打分
        ↓
输出排序列表：分数 + 匹配理由 + 缺口项
```

HR 打开看到的是「这份简历为什么排第一、差在哪」，而不是一个黑盒分数。

### ② 招聘题目发布

- HR 从 6600 道现有题库中按技术栈筛选，或自行命题
- 生成带时限的测评链接，发给求职者
- 求职者作答后自动批改，编程题真实编译运行
- HR 侧汇总得分分布，快速识别异常（全对 / 全错 / 作弊嫌疑）

### ③ AI 初步面试与筛选

- AI 按岗位要求对求职者进行初轮面试（可文字可语音）
- 沿用 C 端已验证的五阶段编排与证据化评分
- HR 拿到每人的四维评分 + 关键原话摘录
- HR 只看排名前 N 的求职者，把面试官的时间留给真正值得见的人

**价值点**：把 HR 从"筛 100 份简历、打 30 个电话"里解放出来，只处理 AI 已经筛过、并且能给出理由的一小部分。

## 10.3 技术复用情况

| 现有能力 | 复用程度 | 说明 |
|---|---|---|
| 岗位要求抽取 | ✅ 直接复用 | 同一套 Prompt 模板，输入从"JD"变成"招聘需求" |
| 匹配评分引擎 | ✅ 直接复用 | 打分逻辑与维度权重不变，只是结果视角不同 |
| 题库与组卷 | ✅ 直接复用 | 新增"发布给求职者"的出口 |
| AI 面试编排 | ✅ 直接复用 | 五阶段流程、Agent 简报、证据化评分全部沿用 |
| 代码沙箱 | ✅ 直接复用 | 招聘笔试与练习笔试共用 |
| 素材库模型 | ⚠️ 需扩展 | 见 10.4 |

## 10.4 真正的技术难点

**C 端的匹配依赖用户自填的结构化素材库，B 端没有这个前提。**

求职者只会扔一份 PDF 简历过来，不会有 17 条整理好的素材。所以 B 端需要补上「简历 → 结构化档案」这一环：

| 环节 | C 端 | B 端需要 |
|---|---|---|
| 数据来源 | 用户主动填写，质量可控 | 求职者上传，格式五花八门 |
| 结构化 | 已结构化 | 需要自动解析 + 抽取 + 归类 |
| 冷启动 | 无此问题 | 简历解析失败即无法匹配 |

解决办法是复用 C 端的「简历导入 + AI 拆分素材」链路（3.1 与 4.2），但仍需解决版式差异大、扫描件识别率、经历时间线推断等问题。

**这是 B 端能否落地的关键，也是我们下一步重点投入的地方。**

## 10.5 与 C 端的技术差异

| 维度 | C 端（已上线） | B 端（筹备中） |
|---|---|---|
| 用户角色 | 单一求职者 | HR / 面试官 / 企业管理员 |
| 数据归属 | 个人 | 企业组织，需多租户隔离 |
| 权限模型 | 单用户 token | 角色权限 + 企业内数据可见范围 |
| 核心链路 | 我 → 岗位 | 企业 → 求职者池 |
| 合规要求 | 个人数据 | 求职者简历属敏感个人信息，需明确授权与留存策略 |

## 10.6 当前进展

- C 端：已上线运行，七项核心能力全部可用
- B 端：完成产品设计与技术方案评估，匹配引擎、题库、AI 面试模块的可复用性已确认；简历结构化的冷启动问题是当前攻关重点

## 10.7 衍生方向：C 端与 B 端联动

> **状态说明**：本节为**远期规划**，尚未进入开发。此处只说明产品方向，不涉及具体技术实现。

目前 C 端与 B 端各自闭环：求职者投递、等待、石沉大海；HR 发布、收简历、翻不完。两端最大的价值其实在**连起来**——匹配分不只是一个给人看的数字，它可以变成一次真实的触达。

### ① HR 主动触达高分求职者

匹配分在 B 端变成一张可排序的名单。HR 看到的不是几百份简历，而是按匹配度排好序的求职者池，可以主动向达到阈值（如 80 分）的求职者发起对话。

**为什么要设阈值**：如果任何 HR 都能联系任何人，求职者会被消息淹没，平台迅速变成第二个骚扰渠道。设阈值同时保护了求职者，也让"高分"这个数字第一次具备真实含义——它意味着你更可能被看见。

### ② 双向私聊窗口

- **B 端 → C 端**：HR 在求职者列表里发起对话，打开独立会话窗口
- **C 端 → B 端**：求职者在岗位详情页看到「招聘方在线」入口，可直接咨询

两端共用同一套会话，消息实时送达。

### ③ 联系方式交换

默认状态下，双方在平台内沟通，**彼此看不到真实的手机号与邮箱**。

只有双方都同意后，才解锁联系方式交换。这条规则的意义在于：把"给不给微信"从被动承受变成主动选择。

### ④ 这一步改变了什么

| 现在 | 联动之后 |
|---|---|
| 求职者投递 → 等通知 → 无回音 | HR 主动找到高分求职者 → 直接对话 |
| HR 收几百份简历 → 逐份筛 | 按匹配分排序 → 只看值得聊的人 |
| 匹配分只是一个展示数字 | 匹配分决定谁能联系你 |

一句话：**从「投递—等待」变成「匹配—对话」。**

这也是我们做 B 端真正的理由——不是为了多做一个后台，而是让已经算出来的匹配度，最终能落成一次真实的人和人的对话。
