# 模块七：AI岗位匹配排名计算提速 + 超时兜底

## Context（背景与现状）

当前排名计算（`JobMatchServiceImpl.analyze`，见 [JobMatchServiceImpl.java](file:///d:/xunlei/Trae CN/chuan/backend/src/main/java/com/chuan/module/jobmatch/service/impl/JobMatchServiceImpl.java#L712-L746)）是**一次同步大模型调用**：把全部知识库 + 全部岗位拼成一个请求，用 `chatJson(…, 0.0)` 一次产出完整排名，再 `parseRank` 按 score 降序排序、`gradeOf` 定级、`persistResult` 落库。

问题：单次全量 LLM 输入/输出体量大，冷计算慢、易触发 HTTP 超时。已存在结果缓存（`computeFingerprint + "|rank-v3"`），故「数据无变更秒返回」已部分满足，但冷启动计算是瓶颈。

本模块目标：在**匹配精度、等级判定标准（`gradeOf`，见 L1399）、排序规则（score 降序，见 L1368）三者 100% 不变**前提下，通过「缓存 + 两级并行计算 + 异步任务 + 分批返回」四层优化冷计算速度并彻底消除超时。

## 关键事实（已确认）

- 评分/等级规则全部由 `SYSTEM_PROMPT`（L65-L148）+ 本地 `gradeOf`（L1399）决定；rank-v3 指纹已用于缓存失效。
- `computeFingerprint`（L1156）吃 `knowledgeText` + `jobTexts`；`persistResult`/`readCachedList`（L1187/L1209）读写 `job_match_result` 单行缓存。
- 前端 `runAnalyze`（[JobMatch.vue](file:///d:/xunlei/Trae CN/chuan/frontend/src/views/JobMatch.vue#L1933-L1952)）当前同步 `analyzeJobs()` 后一次性赋 `rankList`；`manualAnalyze` 已有 `analyzing` 防重复；`getLatestAnalysis` 用于回显。
- 每个岗位评分本质是「岗位 ↔ 知识库」独立匹配，系统提示词第 7 条「分数相同时按输入顺序排列」也印证逐岗独立打分；因此**拆分到逐岗并行**不会破坏交叉排序，反而是现有「score 降序」规则的直接映射。

## 实现方案

### 一、后端：两级并行计算（核心提速，规则不变）

1. 新增两个提示词常量（从 `SYSTEM_PROMPT` 逐字拆分，不重写措辞）：
   - `HARD_CHECK_PROMPT`：由原文【一】严重不匹配否决 +【二】硬性条件逐项核对构成；仅输出 `{results:[{jobIndex,jobName,qualified,hardRequirementMisses,coreRequirements,techStack}]}`。
   - `FINE_SCORE_PROMPT`：由原文【三】软性四维打分 +【四】总分合成与渐进扣分 +【输出结构】构成；输入为「知识库 + 单个岗位 + 已知 qualified/hardRequirementMisses」，输出该岗位**完整单条**结果（含四维子分、score、matched/gaps/details/summary/…），并要求与 Level-1 的 qualified/hardRequirementMisses 严格自洽。

2. 计算编排 `computeRankAsync(userId, fingerprint)`：
   - **Level 1（并行）**：对全部岗位并发调用 `HARD_CHECK_PROMPT`，得到各岗位 `qualified` + 硬性缺失清单。
   - **Level 2（仅合格岗位，并行）**：仅对 `qualified=true` 的岗位并发调用 `FINE_SCORE_PROMPT`；`qualified=false` 的岗位直接用 Level-1 结果 + 原渐进扣分规则（score ≤ 55 / ≤ 40）生成完整 VO（details 用硬性缺失项以 `matched=false` 呈现），**不进入精细计算**——硬性未达标占比越高，节省越大。
   - 合并结果 → 复用 `parseRank`/`gradeOf`/score 降序（保持 L1368/L1399 逻辑）→ `persistResult` 落库。

3. 并行执行：新增线程池 Bean（`@Configuration`，固定大小，取 `min(8, 可用核数)`）；用 `CompletableFuture`/`submit` 逐岗提交，批量 `join` 后按完成顺序收口。

### 二、后端：异步任务 + 分批返回（消除超时）

4. 新增 `AnalyzeTaskManager` 组件（`ConcurrentHashMap<String/taskId, TaskState>` 内存注册表，`TaskState{total,done,List<JobRankVO> results,status,error}`，`results` 用线程安全容器）。单实例部署足够；落库缓存已存在的 `latestAnalysis` 兜底持久结果。

5. 新增两个端点（保留旧 `POST /analyze`、`GET /analyze` 兼容）：
   - `POST /api/jobmatch/analyze/async` → `analyzeAsync(userId)`：命中指纹缓存则直接返回「已完成」任务并带全量结果；否则创建任务、提交后台计算、返回 `taskId`。**同一 userId 已有运行中任务时复用其 taskId（幂等防重复计算）**。
   - `GET /api/jobmatch/analyze/task/{taskId}` → 返回 `{status(RUNNING/DONE/ERROR), total, done, progress, partial:boolean, results:[已完成的评分，score 降序]}`；RUNNING 时 `results` 为当前已计算并排序的头部结果（分批返回）；计算完成后 `partial=false`。

6. 超时兜底：由前端轮询天然兜底——后端不设置阻塞等待；若极端场景超过阈值，前端停止轮询并提示「部分岗位计算中，可先查看已出结果」，后台任务完成后结果已落库，前端 `nextTick` 再查询一次即可补全。

### 三、前端体验

7. `api/jobmatch.js`：新增 `analyzeAsync()`（POST `/analyze/async`）与 `getAnalyzeTask(taskId)`（GET `/analyze/task/{taskId}`）。

8. `JobMatch.vue`：
   - `runAnalyze`：改为调 `analyzeAsync()` 取 `taskId`，开启轮询（约 1s 间隔）调 `getAnalyzeTask`；每次把 `results` 赋给 `rankList`（后端已按 score 降序）实现**逐条/分批渲染**；`analyzing` 期间按钮置灰。
   - 进度文案：`已计算 {{done}}/{{total}} 个岗位`，展示在「更新排名」按钮附近。
   - 终止条件：`DONE` 停轮询 + `partial=false`；`ERROR` 显示失败提示；仍在 `RUNNING` 但超过兜底阈值的，保留已出结果并显示「部分岗位计算中，可先查看已出匹配结果」。
   - `loadLatest` 保持 `getLatestAnalysis` 回显不变。

## 复用（不重写）
- `parseRank`、`applyJobMeta`、`gradeOf`、`computeFingerprint`、`persistResult`、`readCachedList`、`enrichRank` 全部复用。

## 改动文件
- 后端：`service/impl/JobMatchServiceImpl.java`（新增两提示词常量 + `analyzeAsync`/`computeRankAsync`/`analyzeTaskProgress`）、新增 `service/AnalyzeTaskManager.java`、新增 `config/AsyncTaskPoolConfig.java`、`controller/JobMatchController.java`（+2 端点）、`vo/AnalyzeTaskVO.java`。
- 前端：`api/jobmatch.js`（+2 接口）、`views/JobMatch.vue`（`runAnalyze` 异步轮询 + 进度展示）。

## 验证
1. 后端 `mvn.cmd -q -DskipTests compile` 无输出即成功；前端 `npm.cmd run build` 末尾 `✓ built in XXs`。
2. 手工验收 5 条：冷计算无超时、进度实时可见、按钮防重复、数据无变更时秒返回（命中缓存）、等级/排序与优化前一致（同一批数据对比前后 `level`、`score`、顺序不变）。
